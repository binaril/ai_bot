## Task 1. Анализ задачи

Постановка задачи: разработать интеллектуального бота.   
Бот должен быстро и точно давать персонализированные ответы на вопросы сотрудников на основе базы знаний, выявлять пробелы в документации и помогать системно улучшать её качество.  
Использовать технологию RAG (Retrieval-Augmented Generation)

### 1.Сравнение LLM-моделей (локальные Hugging Face vs облачные OpenAI / YandexGPT):

|                                    | Локальные HF (Qwen/Llama)                                                                                               | Облачные (OpenAI GPT-5, YandexGPT)                                               |
|------------------------------------|-------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------|
| качество ответов                   | Из коробки на 5-15% хуже точность ответов чем у облачных, но после Fine-tune с базой знаний достигают близкого значения | Превосходят по качеству ответов (меньше галлюцинаций, лучше цепочка рассуждений) |
| скорость работы                    | 1-3 сек. Выше при хорошо подобранном аппаратном обеспечении (высокие требования к GPU, RAM)                             | 2-8 сек. Влияют сетевые задержки, нагрузка на облако                             | 
| стоимость владения и использования | Дешевле при большом кол-ве запросов                                                                                     | Дешевле при малом кол-ве запросов                                                |
| удобство и простота развёртывания  | Сложнее в развертывании. Требуют DevOps, аппаратные ресурсы с GPU                                                       | Значительно быстрее. Требуется получить лишь APIkey                              |


### 2. Сравнение Моделей эмбеддингов (локальные Sentence-Transformers vs облачные OpenAI Embeddings)

|                                     | локальные Sentence-Transformers                                                                                      | облачные OpenAI Embeddings                                                          |
|-------------------------------------|----------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------|
| скорость создания индекса           | Быстрее для начального создания и ежемесячного инкремента (на правильно подобранном оборудовании), нет задержек сети | Медленнее. Влияние сети, квоты токенов                                              |
| качество поиска                     | Качество поиска чуть ниже                                                                                            | Дают лучшее качество поиска за счет более высокой размерности (больше координат)    |
| стоимость владения и использования  | Значительно ниже за счет отсутствия оплат за токены, но требует начальных вложений на оборудование и развертывание   | Высокие затраты на запросы в облако при большом кол-ве документов и обращений к ним |

**Вывод**. Локальные Hugging Face LLM совместно с локальными **Sentence-Transformers** выигрывают для текущего кейса (более 20 тыс документов, частые запросы к базе знаний). 
Дешевле стоимость владения, выше скорость (нет задержек сети, нет API лимитов), полная приватность. 
Но потребуется приобретение серверного оборудования и больше усилий на внедрение и дообучение.

### 3. Сравнение векторных базы ChromaDB и FAISS

ChromaDB и FAISS — популярные векторные хранилища, но с разным фокусом: ChromaDB как полноценная база данных для RAG, FAISS как высокопроизводительная библиотека поиска

|                                           | ChromaDB                                                                                                     | FAISS                                                                                                                                          |
|-------------------------------------------|--------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| скорость поиска и индексации              | Хорошая скорость на небольших датасетах, ограниченно использует GPU, по различным тестам 2-5мс               | значительно превосходит ChromaDB по скорости поиска и индексации, особенно на больших датасетах. Максимально задействован GPU. По тестам <1 мс |
| сложность внедрения и поддержки           | Значительно проще в внедрении и поддержке (прототип за 5 минут)                                              | Требует часы настроек                                                                                                                          |
| удобство в работе                         | Высокоуровневый API, значительно удобней                                                                     | Требуется больше сложного кода, больше бойлерплейта                                                                                            |
| стоимость владения (учёт инфраструктуры)  | Простая инфраструктура, docker контейнер, решение из коробки. Меньше трудозатрат на развертывание и владение | Сложная инфраструктура. Требует самописного сервиса. Больше затрат на развертывание и владение                                                 |

**Вывод**. Для данной задачи не требуется сверхвысокая производительность задержки в несколько миллисекунд допустимы, по всем остальным параметрам **ChromaDB** выигрывает: проще в разработке и обслуживании, меньшая стоимость владения
